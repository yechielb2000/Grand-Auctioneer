# Production readiness: Firebase and AdMob milestone

## Assessment

This repository is a UI/gameplay prototype with Firebase adapters, not yet a Firebase-backed multiplayer game. `main()` initializes Firebase and `AppServices` only when `FIREBASE_ENABLED=true`, but it always constructs the seeded in-memory `GameState`; screens call that state directly. Authentication is exposed on the profile screen, while the Firestore user, property, asset, and auction repositories are not injected into gameplay. Consequently another signed-in user will not see a shared auction, balance, inventory, or property.

## What already works (adapter-level)

- Firebase initialization is opt-in and uses native platform configuration. Google credential sign-in and auth-state watching are implemented. First profile creation uses a Firestore transaction; the adapter maps its own profile fields (`cashBalance`, `reservedBalance`, `gems`, `netWorth`, `photoUrl`, `createdAt`).
- Firestore local persistence is enabled. Profile reads/creation/token writes and owner-filtered property/asset streams exist. Auction active stream and create operation exist. English bid, English settlement, and Dutch claim contain client-side Firestore transactions with basic state, balance, ownership, and time checks.
- FCM requests notification permission after sign-in, saves/refreshes a token, and listens for foreground messages; the UI displays an `outbid` message. Remote Config fetches defaults/values for anti-sniping seconds and daily reward count (one-hour minimum fetch interval). Analytics records app-open and navigation screen events.
- Storage has an avatar upload method. Rewarded-ad initialization and earned-reward callback handling exist behind build flags. The Android manifest currently contains Google's sample AdMob app ID, not a production ID.

These are building blocks only: no Firebase project configuration, security rules, AdMob production identifiers, or backend are included. A successful compile/initialization would not demonstrate production security or an end-to-end connected game.

## Still seeded, disconnected, or incomplete

- `GameState` initializes fixed demo cash, diamonds, starter assets/property, four auctions, bids and rent; changes reset on restart. Auction/map/inventory/reward actions call local methods. No repository hydration, persistence, or account-scoped state is wired. The profile's Firebase account stream is not the source of game balances.
- The Firestore schema is inconsistent with the PRD: adapter fields differ (`gems` vs `diamondBalance`, `photoUrl` vs `avatarUrl`; adapter auction `sellerId`/`currentHighestBid`/lowercase enum names vs PRD `sellerUid`/`currentPrice`/uppercase names). Profile lacks `lastLoginAt`, starter grants are not persisted, and no starter property/items are created at sign-in. Asset/property saves use merge writes without ownership checks in adapter code.
- `placeBid` only accepts English bids. It rejects repeat bidders entirely, even though English bidding should allow outbidding; its per-user `reservedBalance` increment does not first release that bidder's prior escrow. The repository has no sealed-bid submission, blind/Vickrey settlement, or general expired-auction resolver. UI's sealed/Vickrey outcomes use seeded local competing bids. Dutch settlement is represented but not connected to UI/repositories.
- FCM only stores tokens and receives messages. There is no trusted sender, topic/device cleanup, notification-open routing, or outbid/auction-ended producer. Notifications cannot resolve auctions.
- Reward limits/claims and reward grants are local state only; the UI does not persist cooldowns, daily counts, rent collection time, or grant records. With ads disabled, the UI simulates a completed reward. With ads enabled, the callback grants a local balance, which is client-editable.
- Remote Config exposes two values only; it is not security enforcement. Analytics is basic app/screen tracking. Storage has no upload size/type validation beyond a non-empty byte array in client code, and there are no Storage rules.
- Native setup is unfinished for shipping: no `GoogleService-Info.plist` or `google-services.json` is present, Android application ID is `com.yechielb2000.auction_empire`, release signing uses debug keys, and production AdMob IDs/app registration are absent. Confirm package/bundle IDs and configure Android/iOS build/release settings. The Android sample AdMob app ID must be replaced for a real app; iOS AdMob app ID configuration is also absent.

## Security and competitive-settlement blockers

Firestore client transactions provide atomicity and reduce race conditions; they do not make a client trusted. A modified client can fabricate bids, alter balances, claim rewards, transfer ownership, or invoke exposed operations in unexpected order. Production rules must deny arbitrary writes to balances, reserved funds, inventory ownership, auction outcomes, and reward/cooldown ledgers. No rules are supplied, so enabling the current app against a project without restrictive rules risks exposing user data and the economy. Rules can scope reads and tightly limit safe profile/token writes, but cannot securely calculate and atomically settle the game's competitive economy from untrusted client-provided results.

Competitive English/Dutch settlement, sealed/Vickrey privacy and settlement, rent, and rewarded-ad grants need trusted execution to be cheat-resistant. English/Dutch client transactions currently cannot be safely authorized by rules alone. Sealed/Vickrey bids must remain private until close; writing bid values or highest bid to readable auction documents leaks them. FCM sending also requires trusted credentials and must never use a service credential embedded in the app. App Check can reduce abuse but does not replace authorization or trusted settlement.

The PRD's strict Spark-only/no-billing constraint conflicts with the required trusted server execution. Spark can support Firebase Auth, Firestore, Storage, Remote Config, Analytics, FCM delivery, safe profile/token flows, and noncompetitive/demo data within current project limits. It cannot host the Cloud Functions/Cloud Run/other trusted compute needed for secure economy mutations, private-auction resolution, verified ad rewards, scheduled settlement, or notification sending. Until trusted execution is available, ship only a clearly noncompetitive local/demo mode or a read-only/shared-data slice with no valuable or transferable rewards; do not present client-side balances or auctions as secure multiplayer. Verify current Firebase plan/quotas before launch.

## Proposed implementation slices

1. **Project/bootstrap and data contract (Spark-compatible).** Owner creates/registers Firebase app(s); configure native files, stable Android application ID and iOS bundle ID, Google Sign-In provider/OAuth IDs and SHA fingerprints. Align models, serialization, collection paths and PRD fields (or formally revise the PRD). Add restrictive Firestore/Storage rules and emulator-backed rule review before enabling production credentials. Define profile creation/idempotent starter grant and account deletion/data retention behavior.
2. **Auth-backed read-only game shell (Spark-compatible).** Make auth state drive signed-in/out UI; connect profile, property, asset and active-auction streams to repositories; remove demo fixtures from the production path and scope all reads by authenticated identity/visibility. Add safe token lifecycle and explicit loading/error/offline states. Keep mutation controls read-only until an authorization model exists.
3. **Trusted economy/auction API (requires billing/trusted compute).** Choose Cloud Functions/Cloud Run or equivalent trusted service; design idempotent commands and server timestamps. Implement listing escrow, repeatable English bidding/anti-sniping, Dutch atomic claim, expiry/no-bid/refund/settlement, immutable ledger, concurrency and retry handling. Add access rules that permit only server-owned fields to change. Do not launch competitive auctions before this slice.
4. **Private auctions and notifications (requires trusted compute).** Store sealed bids in bidder-private paths, enforce one bid per bidder and close time, resolve first-price/Vickrey server-side, publish only final outcome, and deliver outbid/win/end notifications from trusted code. Add token revocation/cleanup and notification routing. Keep bid payloads inaccessible to other bidders and seller before close as product policy requires.
5. **Rewards and AdMob (split client setup from secure grant).** Register Android/iOS AdMob apps and production rewarded ad units; replace sample ID, use test IDs in development, configure consent/privacy disclosures and app-store declarations. Add load/show state, frequency/cooldown UX and telemetry. For competitive currency, verify rewarded callbacks using server-side verification and grant through the trusted economy API with deduplication; client callbacks alone are not authoritative. Alternatively ship ads for cosmetic/non-economic acknowledgement only.
6. **Operations and release readiness.** Configure Analytics events/privacy controls and Remote Config defaults/rollback-safe bounds; add crash/error reporting, abuse monitoring, budget/usage alerts, backup/export and support procedures. Set up release signing, package/bundle IDs, FCM platform credentials/APNs, consent flows, and platform store declarations. Stage with emulator/dev project, then limited closed testing before enabling public economy writes.

## Inputs needed from the owner

- Firebase project ID and intended environment split (development/staging/production); confirm whether a paid billing plan and trusted compute are acceptable. If Spark is mandatory, confirm the first release is explicitly noncompetitive/demo or read-only for economy features.
- Android application ID and iOS bundle ID to register; Firebase native config files (`google-services.json`, `GoogleService-Info.plist`) delivered through the project's secret/config process, not committed. Google Sign-In OAuth client setup, Android SHA-1/SHA-256 fingerprints, and iOS URL scheme/client details.
- Desired Firestore region, data retention/account deletion policy, read visibility for users/properties/assets/auctions, and approved canonical schema (current PRD and adapters disagree). Any rules/index policy must follow that contract.
- Storage bucket/region and avatar limits (allowed image types, maximum size, public vs authenticated access); FCM APNs authentication key/capability for iOS and intended notification types.
- Remote Config initial values/rollout owner; Analytics consent/collection policy and required events.
- AdMob account/app registration for Android and iOS, production app IDs and rewarded unit IDs per platform, test-device IDs, approved reward catalog/limits/cooldowns, consent/age/region requirements, and decision on server-side verification. Do not supply account passwords or service-account private keys in chat/source.
- Release signing ownership and final store display name/package metadata. Android release currently signs with debug configuration.

## Recommendation

Proceed with slices 1–2 as a Spark-compatible Firebase milestone and keep all economy-changing controls disabled in that connected build. The first production-capable competitive milestone is not achievable under the spec's Spark-only constraint: it requires owner approval for trusted server execution (and associated billing), plus the project inputs above. Until then, label the app/demo mode clearly and do not issue transferable or valuable in-game rewards.
